我想解决一个这样的问题，因为我经常用opencode，claudecode这类agent，但是因为每日免费模型的token量是有限的，经常会出现一个任务没有执行完，模型用量就到顶了，只能切换其他模型以及重新打开一个命令窗口，或者更换其他Agent来重新执行任务，我需要让Agent能够先对我的提问/需求，首先制定出执行计划，并将总的执行计划写入到文件中（.md），同时在切换模式或者执行任务真正开始后，Agent能够实时更新执行日志，能够详细清晰的将具体情况记录下来，这样处理之后，后续重新打开窗口或者更换模型，使用其他Agent时，能够快速继续任务，从而节省任务执行时间并提高任务效率和任务执行准确性连贯性。根据我的需求，给我推荐一些技术方案，包括并不限于从提示词，skill，插件，重新打造Agent等多角度进行方案规划



针对你遇到的“**免费模型 Token 额度用尽导致任务中断、频繁切换模型/Agent 导致上下文丢失和重复劳动**”的问题，其核心本质是**“外部状态持久化（External State Persistence）与上下文解耦”**。

即：**不依赖 Agent 自身的会话记忆（Session Memory），而是将任务状态、步骤与执行日志下沉到工作目录的文件系统（或外部存储）中**。

以下从 **提示词/规则层（零代码即用）**、**工作流规范（记忆库模式）**、**Skill/MCP 插件层**、以及 **重新自研/编排 Agent（终极解法）** 四个维度为你提供完整的技术方案规划：

---

### 方案一：提示词工程与项目级规则规范（零成本、最快落地）

在 Claude Code、OpenCode、Aider、Cursor 等工具中，它们都原生支持读取项目根目录下的全局规则文件（如 `CLAUDE.md`、`.cursorrules`、`opencode.json` 或直接在初始 prompt 中注入）。

#### 1. 核心思想：定义“双轨文件机制”
要求 Agent 在任何编码或复杂任务前，强制维护两个文件：
- `TASK_PLAN.md`：全局规划、里程碑、原子任务清单（状态机）。
- `EXEC_LOG.md`：执行流水账、每次调用的输入输出摘要、关键决策与踩坑记录。

#### 2. 系统提示词模版（可直接写入 `CLAUDE.md` 或作为初始 Prompt）
```markdown
# 任务执行与状态恢复协议 (Task Execution & Recovery Protocol)

你必须遵循严格的持久化工作流，以防会话中断：

## 阶段 1：需求分析与规划（强制前置）
在执行任何代码修改或环境配置之前：
1. 分析用户需求，在根目录创建或更新 `TASK_PLAN.md`。
2. 任务必须拆解为原子子任务，采用以下格式：
   - [ ] 任务编号: [模块名] 简要描述（必须具备可验证的标准）
3. 询问或等待用户确认，或直接进入执行阶段（按指令要求）。

## 阶段 2：执行与实时日志（强制实时更新）
1. 每开始一个子任务，在 `TASK_PLAN.md` 中将其标记为 `[-] 进行中`。
2. 子任务完成后，必须将其更新为 `[x] 已完成`。
3. 同步在 `EXEC_LOG.md` 末尾追加详细记录：
   - **时间/步骤**：Step X - 任务名称
   - **执行操作**：修改的文件、运行的命令、关键参数
   - **产出与验证**：测试结果、编译状态或输出日志摘要
   - **遇到问题与规避方案**：任何报错及解决方式
   - **当前现场上下文**：如果此时中断，下一个操作应该是什么

## 阶段 3：会话恢复与接力机制
当你看到工作区已存在 `TASK_PLAN.md` 和 `EXEC_LOG.md` 时：
1. 严禁从头重新规划！首先通读这两个文件。
2. 找出第一个未完成的 `[ ]` 或 `[-]` 任务。
3. 查看 `EXEC_LOG.md` 最后一项，恢复上下文，向用户汇报当前断点，并直接继续推进。
```

#### 3. 换模型/重开窗口后的“极简接力指令”
当你切换模型（例如从 Claude 切换到 DeepSeek/Qwen）或换用其他 Agent 时，新会话只需发送一句话：
> “*由于此前模型额度耗尽，会话已重置。请直接读取根目录的 `TASK_PLAN.md` 和 `EXEC_LOG.md`，检查目前执行到的具体进度和最新状态，不要做重复工作，直接从下一个未完成步骤继续执行。*”

### 方案二：借鉴成熟范式——Cline 的 Memory Bank（记忆库）架构

开源 Agent（如 Cline / Roo-Code）之所以跨模型能力极强，核心在于其成熟的 **Memory Bank 模式**。你可以将该规范直接移植到你的工作流中：

在项目根目录下建立一个 `.memory/` 目录，包含以下文件：
1. `projectbrief.md`：核心需求、业务目标、范围边界（很少变动）。
2. `systemPatterns.md`：技术选型、架构模式、编码规范。
3. `activeContext.md`：**当前焦点**。记录“正在做什么”、“接下来 5 分钟要做什么”、“阻碍是什么”。
4. `progress.md`：**进度大盘**。已实现功能列表、未实现功能列表、已知问题。

**优势**：
- 结构非常清晰，当一个模型额度耗尽后，无论新模型理解力如何，只要读了 `activeContext.md` 和 `progress.md`，它的思考直接聚焦在最狭窄的断点处，**极大降低了新模型的 Token 消耗（无需把以前的大量聊天历史全喂给它）**。

### 方案三：Skill / MCP（Model Context Protocol）工具扩展方案

纯靠 Prompt 有时会被模型“偷懒忽略”（特别是低参数量免费模型）。通过定义 **Tool / MCP Server**，将“写计划”和“记日志”固化为模型必须调用的系统函数，能实现 100% 的确定性。

#### 1. 打造一个通用的 Task Manager MCP Server
Claude Code 和现代 Agent 都支持挂载 MCP Server。你可以用 Node.js 或 Python 编写一个极简的本地 MCP 服务，暴露以下工具给 Agent：
- `init_task_plan(plan_markdown: string)`: 强制创建并校验计划文件。
- `update_step_status(step_id: int, status: "pending"|"in_progress"|"done", log_entry: string)`: 每次执行完动作必须调用。
- `get_resume_context()`: 新会话启动时一键拉取当前断点及后续任务。

#### 2. 本地 CLI / Git 自动化 Hook 配合
- **Git Micro-Commit 策略**：在 Agent 的工具链中，强制让 Agent 每完成一个原子任务，不仅写 log，还执行一次 `git commit -m "checkpoint: step X completed"`。
- **优点**：即使 Agent 执行中途写烂了代码，或者切模型时新模型犯蠢搞砸了代码，你随时可以通过 Git 快速 diff 查看上一个模型到底改了什么，甚至 `git reset` 回滚到上一步的安全存档点。

### 方案四：自研/封装轻量级“多模型容灾”Agent 框架（终极解法）

如果你有 Python/TypeScript 开发能力，想要一劳永逸解决**“手动切模型、手动换终端、手动复制粘贴上下文”**的繁琐过程，可以自己封装一个 Orchestrator（编排器）。

#### 架构设计：双层 Agent + 自动 Fallback 机制

```text
[用户需求] 
    │
    ▼
┌────────────────────────────────────────────────────────┐
│ 1. 规划器 (Planner)                                    │
│ - 生成结构化 DAG / Step 列表                             │
│ - 状态下沉到 SQLite / 本地 task_state.json               │
└────────────────────────────────────────────────────────┘
    │
    ▼ 循环派发 Step
┌────────────────────────────────────────────────────────┐
│ 2. 执行器网关 (Executor Gateway - 基于 LiteLLM)          │
│ ┌──────────────┐     429 RateLimit     ┌─────────────┐ │
│ │ 默认模型      │ ─────────────────────> │ 备用模型 1   │ │
│ │ (如 Claude)  │                       │ (DeepSeek)  │ │
│ └──────────────┘                       └─────────────┘ │
│                                               │        │
│                                      429 RateLimit     │
│                                               ▼        │
│                                        ┌─────────────┐ │
│                                        │ 备用模型 2   │ │
│                                        │ (Gemini/Qwen) │
│                                        └─────────────┘ │
└────────────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────────────┐
│ 3. 状态与现场快照 (State Store)                         │
│ - 自动生成并同步 TASK_PLAN.md & EXEC_LOG.md            │
│ - 保存运行时上下文变动，无缝透明迁移                     │
└────────────────────────────────────────────────────────┘
```

#### 关键实现技术栈：
1. **统一模型网关（LiteLLM）**：
   - LiteLLM 原生支持 `fallbacks` 和 `retry` 策略。
   - 当检测到 API 返回 HTTP 429（Token 达到配额）或网络超时，LiteLLM 可以在**代码底层自动无缝切换到下一优先级的免费模型**，而上层的执行逻辑完全不中断。
2. **状态持久化引擎（LangGraph 或自研状态机）**：
   - 使用 **LangGraph** 的 `MemorySaver` / `SqliteSaver` Checkpoint 机制。
   - 它的核心机制就是：图（Graph）的每一步（Node）执行完毕后，自动把当前的全部 State 序列化到 SQLite。即使你强行 `Ctrl+C` 杀掉进程或模型报错，只要重新传入同一个 `thread_id`，它就会读取最新 Checkpoint 继续执行。
3. **输出同步器（Sync Markdown Hook）**：
   - 在图的每一个节点执行后挂载一个 Hook，将最新的 State 抽取渲染为 `TASK_PLAN.md` 和 `EXEC_LOG.md`，方便你随时在 VS Code 或编辑器中实时查看进度。
