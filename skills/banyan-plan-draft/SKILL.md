# Banyan 计划起草技能

你必须在任何代码修改前，将需求转化为结构化的分阶段实施计划。计划格式遵循 iot-kernel 跟踪表规范，并同步初始化 Banyan 双轨文件。

## 触发前置

1. 读取 `references/iot-kernel-format.md` 了解 iot-kernel 计划格式规范。
2. 读取 `templates/plan-template.md` 获取可直接填充的模板。
3. 如果工作区已存在 `TASK_PLAN.md` 且有未完成步骤，先确认用户是要追加/替换/新建，禁止自动覆盖。

## 拆解方法

1. 将需求分解为 **4-8 个原子步骤**，每个步骤必须：
   - 有明确的可验证标准（如 `cargo test --workspace 全绿`、`grep "pub fn encode_" 除 X 外全 Result`、`新增 N 个单测`）
   - 可独立验证（不依赖后续步骤的输出）
   - 标注前置依赖（如有 `P1-1 完成后才可启动 P1-2`）

2. 识别 `Step0`（阻塞修复）：如果有阻塞后续所有步骤的编译错误或基础缺陷，标记为 Step0 优先处理。

3. 明确 `延后声明` 节：列出本轮明确不做的事（防止范围蔓延）。

## 输出产物（全部必须写入文件）

### 产物 1：dated 计划文件

写入 Banyan 根目录，命名格式：`YYYY年M月D日-P{N}实施计划.md`（如 `2026年9月16日-P2P3实施计划.md`）。

严格遵循 `templates/plan-template.md` 格式，必须包含以下节：

```
# [标题]（YYYY年M月D日）

> 来源：……
> 用户决策（已确认）：**……**
> 前置基线：……
> 本文件为执行跟踪表，随执行情况和结果动态更新状态。

图例：⬜ 待开始 / 🟡 进行中 / ✅ 已完成 / ❌ 受阻 / ⏭️ 跳过（本轮不做，留后轮）。

## 状态总览
| 阶段 | 内容 | 状态 | 备注 |
|------|------|------|------|
| P5-0 | 残留硬伤小修（0.5天） | ⬜ 待开始 | …… |
...

## P5-0 拆解
| 子项 | 文件:行号 | 改法 | 状态 |
|------|-----------|------|------|
...

## 验证门禁（每阶段）
...

## 延后（本轮不做，仅跟踪）
...

## 执行日志
...
```

### 产物 2：TASK_PLAN.md

写入 Banyan 根目录 `TASK_PLAN.md`（覆盖或新建），严格遵循 CLAUDE.md 格式：

```
# 任务总体执行规划: [标题]

> 创建/更新时间: YYYY-MM-DD HH:MM
> 当前状态: 规划完成

## 执行进度清单
- [ ] **步骤 1**: [描述]（可验证标准：……）
...

## 关键决策与约束
- [技术选型]
- [边界条件]
- [禁止事项]

---
*本文件由 Agent 实时维护，严禁手动随意擦除或修改状态。*
```

## 约束

- 规划阶段禁止修改任何代码文件。
- 步骤数量严格 4-8 个，多于 8 个必须合并或分轮。
- 每个步骤必须附 `可验证标准`，无标准的步骤视为不完整。
- `关键决策与约束` 节不可留空；若用户无特殊要求，至少写明技术边界和禁止事项。
- `延后声明` 节不可省略（即使为空也须声明"本轮无延后"）。
- `勘察结论（冻结）` 节：若前期做了代码勘察，必须列出冻结结论，执行中不可静默修改。
